# opt-chat guide

Everything the [README](../README.md) leaves out: the page, imports, attachments,
your Claude Code setup and subagents. Written 2026-10-12.

## The page

`./opt-chat` prints the chat's address and opens it in your browser. The
terminal then shows only how the summaries come along and any warnings;
Ctrl-C there quits, stopping every call and subagent underway and logging
what was waiting. `-repl` chats in the terminal instead, as plain lines,
which is handy to script.

The page works like Claude Code:

- The reply streams in as it is written, as Markdown with highlighted code.
  Each tool call is one line, `Bash(ls -la)`, with the first lines of its
  result under it (`Read 12 lines`, `Updated with 2 additions and 1
  removal` for files); click it, or Enter on it, for the whole input and
  output. A call that ran a second or more shows how long after it,
  counting while it runs. A spinner tells what Opt is doing, for how long and how many
  tokens it has written so far; click its `esc to interrupt` to stop.
- The page stays quick however long it is open: the log is virtualized
  ([virtua](https://github.com/inokawa/virtua) on Preact), so only the
  messages in view and near it are in the page, and while you are at the
  end it keeps at most 3,000 messages, down to 1,500 at a time; scrolling
  up brings older ones back. The browser's own find (⌘F) sees only what is
  in the page; Opt's `search` covers the whole chat.
- The input stays put at the bottom: Enter sends, Shift+Enter starts a new
  line, Up and Down go through your earlier messages. Output never touches
  what you type.
- While Opt works, Enter queues a message. It shows under the spinner,
  where you can edit it, take it out, or send it now (⌘/Ctrl+Enter), which
  stops the turn and sends the queue at once. Otherwise it reaches Opt as
  soon as Opt could read it: at once while a tool call runs, with that
  call's result; else at the next tool call; else it starts the next turn.
  Up on an empty input takes the last queued message back to edit.
- Esc stops the turn, keeping what Opt had written, marked Interrupted
  (`[interrupted]` in the log); your queued messages come back into the
  input, as in Claude Code.
- Attach files by dropping them on the page (a file from Finder, or the
  thumbnail ⌘⇧4 leaves in the corner), by pasting with ⌘V or Ctrl+V
  anywhere on the page (a screenshot copied with ⌃⌘⇧4, an image copied
  from a page, a file copied in Finder), with 📎, or by typing a path,
  `/…` or `~/…`, which shows the file it attaches above the input (×
  leaves it as text). A hidden file or folder (`~/.zshrc`, `~/.ssh/…`) is
  only attached once you press its +, and a path in a block of code, or
  in a message naming more than ten, is just text. Images and PDFs go to
  the model as such; text files are inlined; any other file goes as a path
  its tools can read. See [Attachments](#attachments).
- `@` and part of a path opens a menu of the files and folders it
  completes to, as in Claude Code: a folder's entries (`@~/dev/`, `@../`,
  `@src/ap`, relative to `-cwd`), and for a name alone also the files below
  `-cwd` that have it (a quarter of a second's search). ↑/↓ choose, Tab or
  Enter takes one: a folder opens on its own entries, a file goes in as
  `@~/path` (a space in it escaped, `My\ File.png`), which attaches it as a
  typed path does. Esc closes the menu.
- Scrolled up past a long reply or tool output, a round ↑ at the log's
  bottom right (or Alt+U) goes up to your last message out of sight above,
  and each press after to the one before, as in UniiChat's [pull request
  23](https://github.com/VictorTaelin/UniiChat/pull/23).
- Alt+V (or `/view`, or `Opt's view` in the bar) shows the chat as Opt
  sees it instead of the log, after UniiChat's blocks: each line of the
  view, oldest first, as `id+n` and its summary; a line not summarized yet
  says so (a message's shows its head). A click (or Enter) opens a line
  into its two halves, as Opt's `zoom` does, down to the message whole;
  `fold` shuts one, `fold all` goes back to the view. Each line's halves
  are asked for as it opens, so it costs only the view however long the
  chat is. Off by default; Alt+V again goes back to the log.
- Alt+O puts a subagent full screen, the bar talking to it instead of
  Opt; Alt+O again goes back to Opt (see [Subagents](#subagents)).
- `/tree` (or `tree ↗` there) opens the whole memory in a new tab, as
  UniiChat's `/tree` does: the view, the messages, and each level of the
  tree (`L0`, a line per message, up), a page at a time, read-only.
- A long message of yours shows folded, as a big paste does in Claude Code.
- A copy from a reply keeps its lists' numbers and bullets (`1.`, `-`, nested
  ones indented), as a copy from the terminal does.
- Scroll up for the whole chat, back to its first message, loaded as you go.
  A reload, a second tab or another window shows the turn underway,
  mid-reply; a page that loses opt-chat reconnects by itself, also after a
  restart.
- Alt+P (or `/model`, or the model in the bar) opens the model picker, as
  in Claude Code: Claude Code's own list of models, ↑/↓ or a number to
  pick, ←/→ for the effort. Enter keeps the choice for later runs too (in
  `<dir>/settings.json`; a `-model` or `-effort` flag wins over it), `s`
  for this run only, Esc cancels. `/model opus` and `/effort high` switch
  them until you quit. `/agents` lists the subagents at work, `/help` the commands.
- `/reload` rebuilds opt-chat from its source and restarts it in place (see
  Reloading).
- `/status` shows how things stand, as in Claude Code: Claude Code's
  version and the account it is signed in to, then the models,
  efforts and mode of turns, subagents and compactions, the log and the
  view's size, the compactions still to run, the last turn's usage and
  cache share, the plan's usage limits, and the MCP servers connected at the
  last call. It takes a second or so the first time: it asks Claude Code.
- `/usage` shows the plan's limits as bars, with when each resets, and the
  usage credits spent. It also shows where the week's usage went (Claude
  Code, Chats, Cowork) and what used it on this machine: long contexts,
  subagents, skills, MCP servers. All of that comes from Claude Code, across
  all of its sessions. Then come opt-chat's own calls: their cost at API
  list prices, requests, API time and share read from the cache, by model
  and by caller (the chat's turns, each subagent, compactions, side
  questions). `/usage week` covers the last 7 days, `/usage run` this run;
  the default is today. Each call's spend is kept in `usage/` as its
  results come. A resumed subagent's session counts from its last run's
  totals, so that part is subtracted, as `get_usage` tells it.
- Alt+K (or 🎙 in the input) records a voice message, as in Telegram:
  the microphone's level shows as you speak. Alt+K or Enter sends it,
  together with what the input holds (its text, a screenshot), Esc drops
  it; it is sent at ten minutes. You can type, paste and attach while it
  records, Shift+Enter breaking the line. See [Voice messages](#voice-messages).
- `/name` runs one of your skills, as in Claude Code: the line goes to Opt
  and Claude Code runs the skill, with what follows the name as its
  arguments. Typing `/` lists the commands and your skills (a plugin's by
  their own name too): ↑/↓ choose, Tab completes, Enter runs the chosen
  one, Esc shuts the list. A line starting with any other `/word`, or with
  a skill turned off in `/skills`, is not sent: it comes back to the input.
- `/btw question` asks a side question, as in Claude Code. You can ask it
  while a turn runs, and it neither waits for the turn nor stops it. Opt
  answers from the same view a turn reads, so the call reads the turns'
  cache. It also gets the recalled messages and your side questions of the
  last 12 hours (up to 20). It can look in the chat with `zoom`, `search`
  and `date`. It can't change anything: `spawn`, `tell` and any call that
  would ask your permission are refused. The question and answer show set
  apart, after the message they followed, and are kept in `btw/`. They never
  join the log, so no turn sees them and no summary holds them.
  A skill completes mid-text too, as in Claude Code: `/` and part of its
  name after a space lists your skills, and Tab or Enter puts the name in
  (Enter sends nothing there).
- Shift+Tab cycles the permission mode, as in Claude Code: manual (only
  reads go ahead unasked), accept edits (file edits too), auto (whatever
  Claude Code's classifier deems safe). The switch reaches the turn and
  subagents underway. A call Claude Code asks about shows its command or
  change and waits, with the keys, unless you are typing (then Tab or a
  click goes to it, so a key meant for your message never answers it):
  1 or Enter says yes, 2 yes and don't ask again (for this run, its later
  calls too; nothing is written to your Claude Code settings), 3 or Esc
  no, which stops the turn so you can say what to do instead. A subagent's
  questions show its name, and a no lets it go on. In the terminal (-repl),
  the next line answers: y, a, n, or anything else for no with that line
  sent to Opt as what to do instead.
- The bar at the bottom shows the memory: messages (all of the chat's, kept
  for good), the view's size as kept (what each turn reads instead of the
  whole chat; behind a backlog a turn reads it merged further, and Opt's
  view, Alt+V, shows that, with its size in UTF-8 KB), what is left to summarize and the summary lines written since
  opt-chat started, and the last turn's tokens: `in`, its context (what its
  biggest request read: the view, the prompt and tools, your message, its
  steps), and `out`, what Opt wrote. Hover over each for what it is. The spinner shows the context as the turn goes. It shows your
  plan's limits too, as Claude Code's status line can: `5h 10% · 7d 31%`,
  and any other window while it is in use (a model's weekly one, or
  credits), with when each resets on hover. Every call reports the two
  windows as it starts; the page asks Claude Code for all of them
  (get_usage) after each turn, at most once a minute. `?` on an empty
  input lists the shortcuts. While a reply lands in a tab in the background, its title
  says so.

## In the terminal

In `-repl`, type a message and press Enter; a paste of many lines stays one
message, and a path you type attaches its file. Ctrl-C stops the turn, or
the wait before it, and prints the queued messages it held back; Ctrl-C when
idle, or Ctrl-D, quits. After each turn a dim line shows cache use for the
view, for the turn, and for the compactions run since the last turn.

## Reloading

`/reload`, on the page or in the terminal, or `kill -USR1 <pid>` from a
shell, a script or Opt's own Bash, puts a new build of opt-chat to work
without a new terminal:

1. It runs `go build -o opt-chat.new .` in the folder of the running
   binary (which must hold opt-chat's source, as after `go build -o
   opt-chat .`), and runs the build once with this run's flags, as a
   check that it starts. If either fails, nothing changes: the page shows
   the error, and opt-chat goes on.
2. It renames the build over the binary.
3. It waits until the chat is idle: the turn underway ends, and the
   messages waiting get their turns. A message that comes after that, in
   the second or so the restart takes, is logged unanswered.
4. It stops every call, as a quit does. Each subagent at work is cut off:
   its record says so, and the chat gets no report for it. A subagent at
   rest just ends; a `tell` resumes it later.
5. It execs the new binary in place: the same process, terminal, folder and
   flags (less `-import`, and with `-open=false`), so the same page port
   and key. The page reconnects by itself.

If the exec fails, opt-chat goes on as it was, and resumes the subagents it
cut, as at a start.

With `-auto-resume` (on by default), every start resumes the subagents
cut off mid-task: by a reload, by Ctrl-C or another quit, or by a crash.
Each goes on from its saved session, with all it knew, and gets this
message: opt-chat restarted while you worked; your last tool call may have
been cut off, so check its effect before redoing it, then go on with your
task. The chat gets one line, `[opt-chat] Started again, and resumed …
[A], [B]`, which starts no turn; each one reports when done, as usual. A
loop goes on with the turns it had, so its `max` holds across restarts.

These are not resumed: one the user stopped from the page, one that
failed, ended or was at rest, one cut off over a day ago, and one already
resumed 3 times in a row without a result in between (in case it is what
ends opt-chat). For those cut off, the chat gets a report instead, saying
why; a `tell` still resumes them. After a crash, a subagent's Claude Code
can still be at work, its turn going on without opt-chat. The start stops
it first (its process group, if its command line still names its session),
so two calls never share a session.

The chat's own turn, cut off by Ctrl-C, another quit or a crash, is
resumed too (a reload waits for it instead): `turn.json` keeps it while it
runs. The start logs `[opt-chat] Quit while Opt's turn was underway,
cutting it off, and has started again: nothing was lost, go on with that
turn.`, and a turn starts on it. As with subagents, one cut off over a day
ago, or resumed 3 times in a row, gets the note alone, and so does any with
`-auto-resume=false`. A turn that ends short in any other way leaves a note
Opt reads at its next turn: `[opt-chat] Stopped by the user.` after Esc
(`…, who sent the next message at once.` after send now), or `[opt-chat] No
reply: <why>. Send a message to try again.` after a failure.

What a restart loses: the tool call each subagent, or the chat's turn, was
in (each is told to check it), and a question waiting on you. Air and other file watchers are not used
on purpose: subagents edit opt-chat's own source, and each save would
restart it. Keeping the calls themselves alive across a reload is Stage 2,
not built: see the [notes of 15 October](2026-10-15-hot-reload-stage2.md).

## Who can reach the page

Only this machine: opt-chat listens on 127.0.0.1, and answers only requests
addressed to `127.0.0.1:port` or `localhost:port` (so a web page can't reach
it through a DNS name of its own) that carry the chat's key. The key is in
the address opt-chat prints; opening it once stores the key in a cookie
(HttpOnly, SameSite=Strict) and drops it from the address. Requests from
another site's page are refused, the page runs only its own scripts and
styles, and a reply's HTML is sanitized before it shows, so it can't run
code or restyle the page. Files you attached are served
only as images or PDFs; anything else downloads, and none of them runs a
script. The key and the port are kept in `<dir>/web.json`, so a page left
open carries on after a restart; delete the file for a new key.

## Importing past chats

`-import` brings chats from before opt-chat into its memory, as UniiChat's
"Import my past AI chats" does:

- `~/.claude` (or a project under it): Claude Code's sessions, and, from its
  `history.jsonl`, your own messages in the sessions whose transcripts are
  gone (Claude Code deletes them after 30 days, unless `cleanupPeriodDays`
  in its `settings.json` says otherwise), without commands, pastes in full;
- `~/.codex`: Codex's sessions;
- a Claude or ChatGPT data export, its `.zip` or the `conversations.json`
  in it;
- one session's `.jsonl`;
- any other file: each line becomes a `note`.

Each session goes into the log oldest first, under a note naming it
(`Claude Code session <id> in ~/dev/x, from 2026-08-01 10:00:00 UTC (imported)`),
each message at its own date, so `date(id)` tells when it was said. The
user's and the assistant's words come in, with their images; tool calls and
results only with `-import-tools`; sessions run in a directory you name in
`-import-skip` (`-import-skip dev/bots,scratch`) not at all; thinking,
Claude Code's own commands and notices, and subagents' sessions never.
Before it writes anything, the import
says how many messages it adds and about how many compaction calls
summarizing them takes, and asks: the log is append-only. Importing again
adds only what is new since, so a session that went on comes in where it left
off, and a line that a forked or resumed session copied comes in once.

Then the chat starts and summarizes the import, 8 compactions at a time
(`-jobs`), the chat's own lines first, and you can chat at once: as in UniiChat, a turn answers meanwhile from the tree
as far as it is built (see [design notes](2026-10-12-design.md), point 7), and the spinner says how many messages
it sees unsummarized. The bar at the bottom of the page, and the terminal
each minute, say how many are left and how many lines have been written:
merges of older lines go first, so the count of messages stays put for
hours, and then falls. Quit whenever you like: the next run goes on where
this one stopped.

## Attachments

Each file you attach is kept in `files/`, named by its content, and your
message gets a mark for it, which the model and its summaries see:

```
<attachment name="Screenshot 2026-10-10 at 13.48.30.png" path="~/.opt-chat/files/<hash>.png" size="2.6 MB"/>
```

- Images go to the model with the message, at most 2000 pixels a side and
  3.75 MB (5 MB in base64, the API's limit), shrunk when bigger: a Retina
  screenshot stays a PNG, a photo becomes a JPEG, turned upright as its
  EXIF orientation says. Only the image as sent is kept. HEIC photos, as
  iPhones and macOS take them, become JPEGs (with macOS's `sips`). An image
  that would take over 400 MB decoded (100 megapixels; 50 at 16 bits) or a
  file over 200 MB is a path, never decoded.
- PDFs up to 20 MB go to the model as documents (a request holds 32 MB,
  and base64 adds a third); a bigger one is a path.
- Text files are inlined in the mark, up to 25,000 characters in one
  message in all; a longer one is a path, which Read opens.
- Any other file is a path the model's tools can read.

An attachment has a place in your message, as in Claude Code: attaching
one (paste, drop or 📎) types `[Image #1]` (`[PDF #2]`, `[File #3]`) where
the caret is, and deleting that takes the attachment off. "Do this
[Image #1], not this [Image #2]" reaches the model as written: each mark
where its placeholder was, each image right after its mark. A file named by
a path you type gets its mark after the path. An attachment with no place
(its placeholder deleted in a queued message's edit) goes at the end. The
page shows each image where you put it.

A message's images and PDFs are part of it. Yours go with your message; a
tool result's images, such as an image file that Read opened, go with its
`echo`. The call sees each after its mark (a tool result's after the
text), and so does the compaction that writes the message's line, which
says in words what they show: such a message is never its own line.
`zoom(id, 1)` gives the message whole, its images in their places (a PDF
there is a path).

## Voice messages

A voice message is your recording, kept in `files/` like any attachment,
with its words. The page posts it to opt-chat, which has it transcribed by
Whisper (`whisper-large-v3`) on Groq and sends it at once, with the
input's text and attachments. The chat shows it as audio that plays, its
words folded under ▾; the model and its summaries get the words in the
mark:

```
<attachment name="voice 0:14.webm" path="~/.opt-chat/files/<hash>.webm" size="86.6 KB">
Hello Opt, this is a voice message test.
</attachment>
```

They are off until `GROQ_API_KEY` is set when opt-chat starts (a key from
console.groq.com): the audio goes to Groq, and nowhere else. The words are
kept beside the audio, as `files/<hash>.webm.txt`, so a voice message a stop
hands back to the input goes again with them. If Groq fails, the recording
is not lost: it stays in the input as a file, to send as a path or take
off.

## Your Claude Code setup

Turns and subagents run with your own Claude Code skills, plugins, MCP
servers (yours, your plugins' and claude.ai's connectors) and settings, as
`claude` run in `-cwd` has them, but never your hooks, CLAUDE.md or
Claude Code's memory, which would make Opt someone else. `-claude-config=false`
runs them bare, as compactions always run.

With `-claude-md` (on by default), they also get the CLAUDE.md files of the folders they
work in, which hold your rules for each repo. Your own `~/.claude/CLAUDE.md`
stays out (`claudeMdExcludes` in each call's settings), and so does Claude
Code's memory. Claude Code loads the CLAUDE.md of `-cwd` and its parents at
the start of each call, and a deeper folder's only once a file in that
folder is read, so the prompt tells Opt to read a repo's CLAUDE.md before it
works there. One loaded mid-call comes after the view, so the view's cache
should hold (not yet measured).

- `/mcp` lists the MCP servers with their status, live as they connect:
  Enter or Space turns one off or on for Opt (kept in `<dir>/settings.json`:
  Claude Code saves no such choice for `claude -p`), `a` signs in to one
  that needs it (the sign-in is Claude Code's own, for every session), `r`
  reconnects one.
- `/skills` lists the skills, each with what its listing costs every turn:
  Enter or Space turns one on or off for Opt, from its next call (kept in
  `<dir>/settings.json` and given to each call as settings; your Claude
  Code keeps its own). A skill your organization or a plugin manages stays
  as it set it.
- `/plugins` lists your plugins, each with the skills, MCP servers and
  tokens it brings: Enter or Space turns one on or off for Opt, all of it
  at once (turn off `figma` and its skills and MCP server go), from its
  next call, kept in `<dir>/settings.json` and given to each call as
  settings (`enabledPlugins`); your Claude Code keeps its own.
- In the terminal, `/mcp`, `/skills` and `/plugins` list them; `/mcp off
  NAME`, `/skills on NAME`, `/plugins off figma@claude-plugins-official`
  and so on switch one.

What it costs: the skills and servers sit in a block Claude Code adds after
the view's first message (with the default setup here, about 20k tokens),
cached with it. Two things keep it cached from turn to turn. Before a call
sends the view it waits, up to 5 seconds, for the MCP servers that were
connected last time to connect again, since the block lists those connected
by then (a server that is always slow is not waited for). And calls run
with `ENABLE_TOOL_SEARCH=true` (MCP tools load when needed, so a server's
hundreds of tools never sit in every prompt) and `CLAUDE_CODE_TETHER_LIVE=0`.
With Claude Code's server-side threads, each request after the first sent
only what was new, and the server wrote the whole block to the cache again
on every turn. Measured on a 27,000-message chat: about 22k tokens written
per turn with threads, a few hundred without.

## Subagents

`spawn(name, task, effort, model, autocompact)` starts a subagent in the
background and returns at once; `effort`, `model` and `autocompact` are
optional (`-agent-effort` and `-agent-model`, Opus, when left out; ask Opt
for "a Fable subagent" and it passes `fable`). A subagent is
a fresh call with the same prompt and tools, which gets the view, then its
task. Its steps go to `agents/<Name>.log`, which `zoom("Name")` opens whole
(Claude Code saves a long one to a file the model reads). Its final reply
comes back as a `work` message, `[Name] report`, ending with the model it
ran on, its context's size and `Full chat: zoom("Name")`. If a turn is running, the report is injected into
it; otherwise it starts a new turn. The chat never waits for a subagent.
While any are at work, a turn's input starts by naming them, as UniiChat's
does, so Opt never starts the same task twice (the line is not logged).
`tell(name, message)` reaches a running subagent between its tool calls. A
subagent that has reported keeps its call open for 30 minutes: a `tell`
then sets it to work again with everything it knew (a review of its own
work, a fix), and it reports again. After that its call ends, but a `tell`
still sets it to work again where it stopped: a subagent's call is a Claude
Code session saved to disk (in Claude Code's own, `~/.claude/projects`;
the chat's own calls are never saved), and the tell resumes it, with all it
knew. One that a quit, a crash or a reload stopped mid-task goes on by
itself as opt-chat starts again (see Reloading); with `-auto-resume=false`,
or when it isn't resumed, its report says it stopped, and a tell resumes it:
the tell's message to it starts by saying its call was resumed, and that
its last tool call may have been cut off. `agents/<Name>.json` keeps what a
resume takes: its session, model, effort and task, its loop and its turns.
A subagent whose session Claude Code no longer has (it deletes old
ones, 30 days by default) can't be resumed; a new one can read its steps
with `zoom("Name")`.
Subagents can't start or tell subagents.

The page shows this run's subagents in a rail right of the chat, when the
window has room for it: each one's state (working and for how long, a
question waiting on you, reported and resting, ended, failed, or stopped
by a restart), its model,
effort and context, and the tool call it is in now, with how long it has
run. Click one to see its steps as they come, from its log, as the chat
shows its own: its task and Opt's tells, its text, its tool calls and their
output; ← goes back to the list. Its stop button ends its call: one at
work stops mid-step, and the chat gets a note saying so, with no report
and no turn; one at rest just ends. Press it again, now clear, to drop it
from the list; its log stays, for `zoom`, and a `tell` still resumes it.
In its view, `compact` compacts its context (see below).
× hides the rail until a new subagent starts, and Alt+A or the bar's
agents show it again. It stops no subagent. In a narrow window the rail is a drawer that the
bar's agents, or Alt+A, open; Esc closes it. Drag the rail's left edge to
widen or narrow it (the browser keeps the width); a double-click on the
edge sets it back.

You can also talk to one subagent directly, as in Claude Code's agent
view, while Opt goes on with its own work (UniiChat's agent tabs show an
agent with the input off). ⤢ on its card or its view, or Alt+O, puts it
full screen: its steps take the chat's place, and the bar talks to it
instead of Opt, marked `→ [Name]` in blue. Send it messages, files and
voice messages, which reach it between its tool calls or set it to work
again, as a `tell` does; answer its questions; see its model, effort and
context (`context`: its task, the first message it got and, once
compacted, its summary). Your messages show as yours, Opt's task and
tells as Opt's. Opt's chat gets a `work` line, `[user → Name] text`, that
starts no turn: Opt knows what you told it. A subagent you set to work
again (after its report, a stop or a restart) answers you alone, in its
view; one you write to while it works on its task, or on Opt's tell,
still reports to Opt at the end, and so does one Opt tells while it
answers you. A command (`/status`, `/btw`) still goes to Opt. While it
works, Esc stops it, not Opt's turn; at rest,
Esc goes back to Opt, as do Alt+O and `← Opt`. Each keeps its own draft,
and Opt's chat stays where you left it. One agent is full screen at a
time: a click on another card puts that one there instead.

A subagent worked through many steps can outgrow its context. Past 400k
tokens (`-agent-compact-max`; `0` turns it off), Claude Code compacts it
between two steps, never in the middle of one, and it goes on with its
task from the summary; its log and the page say so. `/autocompact 250k`
(saved in `<dir>/settings.json`; `/autocompact off` undoes it) compacts
subagents sooner, and `spawn`'s `autocompact` sets it for one; neither goes
past the cap. One that reported past its window is compacted at rest. Once
compacted, its next message after a report brings the view and its task
again, as they are then; a `tell` that comes while it compacts waits for
it. Each report says how big the subagent's context is. The page's
`compact`, in its view on the rail and full screen, compacts one now: at
rest at once; at work at the end of its next step, where opt-chat stops it,
compacts it and sets it to go on with its task. The chat's own calls never
compact, whatever your Claude Code's setting: the view is its memory, and
it never outgrows its size.

### Loops

A subagent can run in a loop, as a Claude Code Stop hook keeps a session
at work. Hooks are off in every call, so opt-chat runs the hook itself.
`spawn`'s `loop` is `{command, dir, max}`. At the end of each of the
subagent's turns, opt-chat runs `command` with `sh` in `dir`. It passes the
Stop hook's JSON on stdin: `session_id`, `transcript_path`, `cwd` (that
is, `dir`), `hook_event_name`, `stop_hook_active` and
`last_assistant_message`. If the hook prints `{"decision":"block",
"reason":...}` or exits 2 with a reason on stderr, the reason goes back as
the subagent's next message. The chat sees nothing. When the hook lets it
stop, its last reply comes to the chat as its report. The loop also stops after `max` turns (60 when left
out), and when the hook fails or takes more than 60 seconds; the report
then says why. A `tell` waits for the turn to end and goes ahead of the
hook's next step. Stop on the page ends the loop. Past its window, the
subagent is compacted between two steps, as any is. The loop
is kept in `agents/<Name>.json`, with its turns since its last report, so a
resumed subagent goes on looping, and a restart doesn't reset its `max`.
After a report, a `tell` starts the loop again.

## Your instructions

`<dir>/AGENTS.md` follows the system prompt, as "The user's instructions".
opt-chat checks the file before each call and reads it again when it has
changed, so an edit, yours or Opt's, reaches the next call; each one starts
the prompt cache over, for turns, subagents and compactions. When you state
a standing rule ("never X", "from now on Y"), the prompt has Opt append it
there, in your words with the id of your message, and show you the line.

## Wake-ups

With `-wake` (on by default), Opt has a `wake` tool. `wake(at, message)` sets a message for
later: `at` is a duration (`90m`, `2h`), a time (`21:30`: today, or
tomorrow once passed) or a date and time (`2026-10-20 09:00`), local. When
it is due, the chat gets `[opt-chat] wake-up you set at <time>: <message>`
as a `work` message, which starts a turn as a report does, or joins the
turn underway. `wake(cancel)` cancels one by its id; `wake()` lists those
pending. Pending wake-ups are kept in `<dir>/wake.jsonl`, so they outlast a
restart; one that came due while opt-chat was down comes once, as it
starts. A turn started only by wake-ups (and reports) sets none until a
message of yours joins it, so they never chain; subagents set none.

```
<dir>/

  files/<hash>.<ext>      attachments and tool results' images, named by their content
  files/<hash>.<ext>.txt  a voice message's words
  web.json                the page's key and port

  agents/<Name>.json      what resuming it takes: its Claude Code session, model, effort, task, state, loop and turns, cut, resumes, pid

  claude-plugin/          the plugin that drops your email from calls' context (-hide-email)
  lock                    one process per chat
```

Back the directory up. Never edit the logs: they are the chat's history.
